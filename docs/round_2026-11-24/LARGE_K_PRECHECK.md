# 大 K 播种前置判据：数据核查与处置建议

**日期**：2026-11-24　**状态**：只读核查完成，**未改生产代码**
**触发**：`out/3E-2_HER_exp1_0150mA/run.log`，DRT 3 峰 → 扫 K=[2,3,4]，K=4 花 366s 后因分级 0 剔除；用户问“能否播种前判断是否要加入 K=4，事后剔除成本太高”。
**更新**：2026-11-24 二次核查——**只看含大 K（K≥4）的案例后，结论反转**：大 K 从未被最终选中，建议从“quick 预筛”改为“前置跳过”。第 2/3 节的旧统计（全样本）保留作反例记录。

---

## 1. 先纠正一个前提：没有“大 K 不播种”规则

`bm_real.py:2852` 的播种唯一门槛是 `if pk else None`（DRT 峰列表非空），与 K 无关。
`adjust_peaks`（:855）明确写“峰数不一致是常态，不能因为峰数对不上就放弃播种”，
K 比峰数多就把面积最大的峰在 lnτ 上对称劈开（dsplit=0.5 decade），无次数上限。
K 范围：`K_drt=min(峰数,kmax)`，扫 `[K_drt−1, K_drt+1]`，K=4 是 K_drt+1 的常规候选。

**“K=4 播种=是”是当前设计的正确行为**；最终选 K=2（K=4 因 R̂=1.053/bulk=85/tail=32 分级 0 被剔除）也是正确行为。问题不是 bug，是**成本高**。

## 2. 全样本统计（已被第 3 节取代，保留作反例）

329 条带 K 扫描日志，把所有“需劈开的 K”（含 K=2、3 这种常规边界）混在一起：

- 峰宽/劈开间距比：崩溃组中位 6.16 vs 通过组 5.46 —— 重叠，无判别力；
- P(峰位出窗)：0.3/0.5/0.7 三档崩溃率 63%/71%、69%/65%、73%/64% —— 无判别力；
- 需劈开的最大 K 共 276 条：分级 0 **184（67%）**、通过 **92（33%）**。

**当时据此建议“不要硬砍、用 quick 预筛”**。二次核查证明这个结论被全样本的异构性带偏了。

## 3. 只看含大 K（扫描范围含 K≥4）的案例——结论反转

**69 条**含 K≥4 的案例（全库 K 扫描日志 329 条中的 21%）：

| K | n | 分级 0 | 崩溃率 |
|---|---|---|---|
| 4 | 69 | 42 | **61%** |
| 5 | 62 | 38 | **61%** |

K=4 按劈开次数拆：

| n_split = K−峰数 | n | 崩溃率 |
|---|---|---|
| 1 | 8 | **100%** |
| 2 | 11 | 45% |
| 3 | 48 | 56% |

K=4 峰宽比分层：BAD 组中位 5.46（min 2.14 / max 9.72），PASS 组中位 4.88（min 3.36 / max 5.50）——
**仍无干净阈值**，不要试图用峰宽比做硬判据。

### 决定性事实：大 K 从未被最终选中

- **69 条含 K≥4 的案例里，最终选中 K=4 的是 0 次；选中 K≥4 的是 0 次。**
- 全库 205 条有最终 K 的日志：K=1 **156**、K=2 **48**、K=3 **1**、K≥4 **0**。
- 那 27 条“K=4 分级≥1（通过）”的案例，逐条核对：全部 `final=K1` 或无 final，
  **没有一条真正选中 K=4**。“通过”只是没被硬剔除，在配对 LOO 分档比较里仍输给小 K。
- 42 条 K=4 崩溃里，只有 7 条是基础 K 也崩（谱本身难）；**35 条是大 K 独自浪费的成本**。

⇒ 第 2 节担心的“92 条大 K 通过、硬砍会丢真实改进”是**全样本假象**：
那 92 条绝大部分是 K=2/3 的常规边界通过，不是 K≥4。聚焦大 K 后，
**通过 ≠ 被选中**，大 K 在本项目语料上的实证收益是 **0 条**。

## 4. 处置建议（修正版）：前置跳过 K≥4，默认不再试跑

既然大 K 在 205 条里 0 次被选中、61% 分级 0、劈 1 次时 100% 崩溃，
再花 standard 预算（本案 366 s）去“确认它不行”没有信息收益。

### 推荐：默认 K 上限随证据收紧，显式升级

1. **默认扫描范围改为 `[K_drt−1, K_drt]`**（砍掉 K_drt+1），
   并对 `K_drt+1 ≥ 4` 的情形直接**播种前跳过**，落 `k_precheck` 块：
   `{"K":4, "n_split":1, "skipped":true, "reason":"empirical: 0/69 selected, 61% grade0", "evidence":"LARGE_K_PRECHECK.md §3"}`。
2. **保留升级通道**：`--krange` 显式指定、`--wide`、或新开关 `--allow-large-k`
   才能跑 K≥4，返回值里标 `large_k_opt_in=true`，不静默。
3. **`k_selection` 明写**：“K=4 未试跑（历史 0/69 被选中，基于 69 条大 K 案例的前置跳过）”，
   不要写成“K=4 被剔除”——它根本没跑，两件事不能混。
4. **不动判据、不动模型定义**：这是“默认搜索范围 + 执行预算”的收紧，
   A1–A4、M-a/M-b/M-c、acf 阈值零改动；升级通道保证需要时仍可访问。

### 为什么不再用“quick 预筛”

- quick 与 standard 不在同一采样尺度（记忆 11-22：quick 判稳不保证 standard 过，R̂ 非单调）；
- 即便 quick 判“稳”，69 条里也没有一条最终选中 K≥4 ⇒ 预筛通过也改变不了结论，
  纯属多花一次 quick 钱。**前置跳过比预筛更省，且信息损失为 0（实证收益本来就是 0）**。

### 边界与风险（必须写进文档）

- 本结论是**本项目语料**的实证（合成 2E/3E + AZ31 系），不是“大 K 永远无用”的物理定律；
  新体系（不同机理、更宽频窗）若 K≥4 真有用，`--allow-large-k` 是逃生口。
- 记录里必须保留 `0/69` 的出处；将来语料扩大到含 K≥4 被选中的案例时，要重新评估这条默认值。
- 若用户不接受“默认跳过”，退路是第 4 节旧方案（quick 预筛），但已证明收益低。

## 6. 已实现（用户 2026-11-24 授权）

**改动**：`bm_real.py` / `bmdrt.py` / `config.json` / `test_entry_parity.py`。

- `LARGE_K_MIN = 4`（固定常量，**不进 config**——它是数据核查得出的事实不是可调超参；
  升级走 `allow_large_k` 开关而不是改这个数）。
- `bm_real.run(..., allow_large_k=False)`：默认路径只跳过 `hi == K_drt+1 且 hi>=4` 这一格。
  **峰数 1/2/5 的谱默认逐位不变**；峰数 3 → 扫 `[2,3]`（跳过 K=4）、峰数 4 → 扫 `[3,4]`（跳过 K=5）。
  `wide` / `krange` / `allow_large_k` 任一为真即恢复旧范围，落 `large_k_opt_in=true`。
- 结果 json 新增 `k_precheck` 块（`K_drt` / `scanned_K` / `skipped_K` 含 K、n_split、理由、出处 /
  `allow_large_k` / `large_k_opt_in`）；`k_selection` 首条写 `K=4 **未试跑** ... **不是「跑了被剔除」**`。
  `k_precheck` 是可选键：旧调用方不传时 json schema 不变。
- `bmdrt.py`：`--allow-large-k` 布尔旗标（只在 True 时写进 cfg，与 `--ref-rwp` 同模式），
  帮助文本已补；`config.json` `fit.allow_large_k=false` + `_说明` 同步。`bm_real.py` CLI 同款旗标。
- `--dry` 的建议命令同步新默认（原来仍建议 `--krange 2,4`，现在给 `2,3` 并提示升级通道）。
